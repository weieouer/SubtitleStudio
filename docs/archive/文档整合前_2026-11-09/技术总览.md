## 1. 项目定位

**本地视频/音频转字幕工作台**，核心能力：

- 字幕提取：本地 ASR 模型识别中文音轨，生成带词级时间的字幕
- 音轨强制对齐：用 Qwen3-ForcedAligner 把人工确认后的字幕对齐到视频音轨，只改时间不改文字
- 剧本参考校验：以 ASR 字幕为主体，反向匹配任意排版的 TXT/MD/DOCX 剧本，给出文本差异和上下文插入提示供人工复核

**不做的事**：声纹分离、多音轨选择、翻译、烧录、自动下载模型、剧本一对多强制对齐、免安装发行、调用云端识别或上传素材到云端。

服务只监听 127.0.0.1，不对外暴露。模型不随项目分发，需自行下载到 `data/models/<名称>/`。

## 2. 技术栈

| 层 | 选型 |
|---|---|
| 操作系统 | Windows x64 |
| Python | 3.13.15（最低 3.12，numpy 2.5.4 / av 19.0.2 要求 `>=3.12`） |
| 后端 HTTP | Python 标准库 `http.server`（无 Flask/FastAPI） |
| 前端 | 原生 HTML/CSS/JS，无 CDN、无前端框架 |
| 音视频解码 | PyAV 19.0.2（携带 FFmpeg 动态库，无需外部 ffmpeg.exe） |
| ASR 主引擎 | faster-whisper 1.2.1（基于 CTranslate2 4.8.5） |
| VAD | Silero VAD（faster-whisper 内置 ONNX 模型） |
| 文本匹配 | RapidFuzz 3.14.6 + pypinyin 0.55.0 + difflib |
| 分词断句 | jieba 0.42.1 + Python 规则 |
| 数值计算 | NumPy 2.5.4 |
| 强制对齐 | Qwen3-ForcedAligner-0.6B（独立子进程引擎） |
| 外部引擎运行时 | FireRedASR2 / Qwen3（ASR 与对齐）通过 `data/engines/<引擎>` 独立虚拟环境子进程调用，避免 Torch/Transformers/NumPy 版本冲突污染主环境 |

当前目录尚未初始化 Git；已提供 `.gitignore`，源码可独立上传，模型、虚拟环境、用户数据和便携发布资源不进入源码版本管理。历史快照保留在 docs/versions 和 docs/archive。

## 4. 核心处理链路

完整链路：**ASR 提取 → 强制对齐 → RMS/频谱边界微调 → Silero VAD 首尾二次校验 → 反向剧本匹配校验**。每步独立可取消、可撤销，前一步的输出是后一步的输入，但文本始终以人工确认为准，算法不自动覆盖文字。

### 4.1 ASR 提取

| 项 | 说明 |
|---|---|
| 输入 | 媒体文件路径、模型名称、设备（auto/cpu/cuda）、VAD 开关、语气词保留开关（`keep_interjections`）、语言（固定中文） |
| 解码 | `media.decode_audio()` 用 PyAV 取第一音轨，重采样到 16 kHz 单声道 float32；相同媒体及采样率优先复用项目内 PCM 缓存 |
| 推理 | `asr.transcribe()` 调 faster-whisper，beam=5、temperature 从 0 起按 0.2 步进回退、词级时间 |
| VAD | Silero VAD ONNX 模型，"仅人声"开关控制提取前的语音区间检测 |
| 语气词 | 关闭“语气词”（默认）时，`core/interjections.py` 的 `strip_interjection_cues()` 直接删除整条只有笑声、叹气、咂嘴或填充音的字幕，并用 `strip_boundary_interjections()` 去掉对白句首、句末及句末标点旁的“啊、呀、哎、唉、哈哈”等独立语气词；句中语气词、引号内对白和“呢、吗、吧”等语法助词保留。开启时保留整条语气词、写 `interjection` 标记并正常导出；校准仍会按可靠参考去掉参考中不存在的语气词 |
| 输出 | `segments[]`，每段含 `text / words[{start,end,probability}] / no_speech_prob` |
| 取消 | 解码前后检查取消；模型加载和片段推理非即时可中断 |
| 内存 | 按媒体时长预分配、容量不足时扩容；PCM命中用只读mmap。长媒体仍有整轨与模型内存占用，不能保证任意低内存机器可运行 |

### 4.2 强制对齐（Qwen3-ForcedAligner）

| 项 | 说明 |
|---|---|
| 输入 | 人工确认后的当前字幕（文字 + 粗略时间）、媒体音轨 |
| 切片 | `alignment._alignment_windows()` 以完整字幕组约230秒窗口，临近上限最多回看30秒寻找字幕间持续静音；首尾在各2秒余量内优先选择静音，无可靠静音时保留上下文；不拆单条字幕 |
| 静音证据 | 整轨20ms RMS、全局底噪与语音能量约束，连续低能量至少80ms，切点两侧各留40ms；用于模型输入窗口，不改变用户的字幕停顿阈值 |
| 统计 | 结果的 `windowing` 保存窗口时间、负责的字幕索引及静音/上下文边界，便于审查 |
| 子进程 | 把每个窗口的音频切片写为临时 WAV，调用 Qwen3-ForcedAligner 子进程 |
| 时长上限 | `duration.duration_bounds()` 按发声字数给出期望时长与上限（0.55 秒/字 + 0.9 秒，最低 1.2 秒、最高 12 秒；标点空白不计）。`audio_boundaries.cap_durations()` 在边界微调后、重叠修复前，对超过上限的条目用 `_speech_runs()`（Silero VAD，缺失时退回 RMS/频谱）和 `trim_to_speech()` 选出覆盖全部词、最贴合词时间的语音段收紧；证据不足时回退对齐前输入时间并标 `alignment_error`，输入时间也超上限时只标 `needs_review`，不硬裁文字音频。长度正常但对齐段语音覆盖低于 35%、粗时间附近明显更高的条目，用 `speech_near()` 重新锚定到粗时间附近的语音段（`speech_reanchor`），处理字幕被句前特效音带走的情况。明细写入 `duration_trim`，对齐信息新增 `duration_repairs` |
| 输出 | 更新后的 `start/end`，保留原始记录；近似文字用字符映射保留词时间，不可靠映射或重叠回退明确标错、清除过期派生时间 |
| 限制 | 大幅错位应先粗调；不宣称整集任意错位搜索 |
| 语言 | 固定 `language='Chinese'`，非中文未打通（见 R13） |

### 4.3 RMS/频谱边界微调 refine_boundaries

| 项 | 说明 |
|---|---|
| 输入 | 对齐后的字幕、媒体音轨 |
| 算法 | `audio_boundaries.speech_intervals()`：基于每条字幕 ±0.35 秒窗口的 RMS/频谱变化；整段音频按1秒块估计全局底噪，局部第20百分位和持续60ms窗口低分位作有限修正，第85百分位作语音参考，使用自适应死区和双阈值 |
| VAD 校验 | `_vad_region()` 对整条字幕（前后各 0.3 秒）做一次 faster-whisper 内置 Silero VAD；`_vad_runs()` 用 0.5/0.35 双阈值、最短语音 128 ms、最短静音 128 ms 压出语音区间；`_vad_start()`/`_vad_end()` 只采纳与首词/尾词重叠最多、且不删掉整词的区间 |
| 调整 | RMS 普通边界在 `max_shift=0.18 秒` 内微调；有词时间、明显语音/底噪反差及持续尾部静音时可额外收尾。VAD 明确判定句首/句尾为非语音时可越过 max_shift 继续收紧，单端最远 3 秒；尾端最多到最后一个词结束时间 +0.15 秒 |
| 不裁条件 | 起点处已在说话、结尾处仍有语音、VAD 区间前/后 96 ms 以上中高概率（≥0.30）或占比 >15%（疑似轻声人声）、区间短于 128 ms、会删掉首/尾词、VAD/onnxruntime 不可用时一律保留原时间 |
| 重叠修复 | 两条重叠时取中点 `(left.end + right.start) / 2`，超过 max_shift 标 `needs_review` |
| 输出 | 微调后的 `start/end`；普通尾部明确静音也记录 `pause_after`，无需先裁掉0.12秒；严重重叠不强行拉散；`audio_refinement.vad_trim` 记录 VAD 建议值及是否采用 |
| 保守策略 | VAD 只收紧、不扩张，结果不会比原 RMS/词时间更差；密集对白场景可能返回空（保留 ASR 原时间），优于误判 |

### 4.4 反向剧本匹配校验

| 项 | 说明 |
|---|---|
| 输入 | ASR 字幕（按时间排序）、完整剧本原文；多份 TXT/MD/DOCX 保留独立 source 身份及原文范围，全文存储顺序与视频演出顺序无关 |
| 实现 | `reference_match.py` |
| 索引 | 对整本剧本 NFKC 标准化、字符位置映射、字符二元组 + 拼音二元组索引 |
| 搜索 | 每条字幕独立搜索 + 按需组合相邻1–4条；已可靠确认跨来源的组合跳过；候选不跨文件边界；重复精确台词按游标补候选 |
| 复用 | 最近一份全文的标准化/拼音/二元组特征缓存；评分参数及范围每次独立应用，候选请求内有界缓存 |
| 评分 | RapidFuzz 字符相似度 + pypinyin 拼音相似度（权重 0.25，上限 0.4）+ 长度差惩罚 |
| 选择 | 按字幕时间推进、记录每个 source 独立游标的动态规划；文件间可切换及返回，同文件内不逆序、不重复占用；全局束64、每活跃来源补充8条、总上限256 |
| 阈值 | 默认最低分 0.64、高分线 0.94、拼音门槛 0.90、候选分差 0.035；1-3 字短句门槛至少 0.88 |
| 上下文 | 相邻唯一长台词锚定局部剧本区间，中间1–3条字幕只允许在该区间对应；全文其他位置偶然同句不能通过。反复或连续的其他来源有独立锚点时保留真实场景切换能力 |
| 输出 | 内部细分高度匹配 / 错字 / 谐音 / 漏字 / 多字 / 未匹配 / 多候选 / 上下文异常；UI通过绿色阶段标签（“校验通过 / 校准通过 / 对齐通过”，显示最后一次检查）、黄色“疑似问题”、红色“明显问题”和红色“语气词”提醒，全文异位候选只读不可采用 |
| 上限 | 剧本合计 ≤ 50 万字符、每次 ≤ 5000 条字幕、单条 ≤ 1000 字 |

前端两排工具：编辑排合并/分段/添加/删除/撤销/重置；处理排关闭导出/重新识别/校准字幕/对齐字幕，后两项只在对齐模式显示。推荐流程是“开始校验 → 校准字幕 → 对齐字幕”：开始校验只按参考标差异、不改字幕和分段；校准按参考修正内容并整理分段，不碰音轨，因此很快；对齐字幕最后按音轨改时间与分段。对齐字幕复用全局`alignAndVerify`，任务只更新时间结构和分段：不运行参考校验、不按参考改字；先按`gap_seconds`停顿阈值拆条（0关闭），有可靠参考时用`_reference_break_at()`检查参考对应位置：参考同一句内按声音停顿决定是否拆，参考里明确是两句话（句末标点或换行）时按句界强制拆开、不受停顿阈值影响；再按`max_width`调用`segment_alignment_cues()`把过长字幕分段衔接后面；只拆不合并、不改字词，两句话连在一起说时保持两条字幕首尾衔接。拆分出的子条由`inherit_reference`继承父参考区间，不重新跑全文校验。校准字幕复用首轮新鲜参考，缺失或过期时按≤5000条（含±3上下文）分请求，所有结果成功后才提交目标更新；先对高度匹配、错字、谐音、漏字、多字等可靠参考采用参考文字（补全漏字、删除多余内容），再按每行字数、标点开关和数字开关整理与呈现。关闭“语气词”时校准直接删除整条语气词并清理句首、句末语气词；开启时保留整条语气词，但可靠参考中不存在的仍删除。校准及重新识别均支持多选/全选。

`/api/segment`增加`mode:calibration`，接收`keep_punc`与`keep_interjections`。调用接口前，前端已对可靠参考采用参考文字，完成漏字补全和多余内容删除；接口再做格式整理，调用`core/calibration.py`：可靠同字参考补回标点→明确句界独立拆条→按`keep_punc`开关去掉标点（开启只留问叹号，关闭全部去掉）→按每行字数切分（停顿拆条由对齐任务负责，校准不重复拆）→按开关删除整条语气词并清理句首/句末语气词→`_merge_same_sentence()`对可靠参考中同属一句的相邻条目自动合并（合并后不超每行字数、两条之间停顿未达`gap_seconds`阈值、无手动拆分/导出状态冲突；参考以句末标点或换行明确分句的保持分开，停顿阈值不参与）→对剩余布局检测单字/双字碎片并写入`merge_suggestion`。`_reference_text()`只采纳文字与字幕逐字相同的可靠参考（高度匹配，或未过期的错字/谐音/漏字/多字，或已确认歧义），即使`script_text`缺失或采用后标记过期，也能从参考原句恢复换行和句末标点，从而把“两句合并成一条”的字幕自动拆成两条；校准不碰音轨，拆分后的时间只是暂定值，由最后“对齐字幕”按音源重算。校准返回`interjections`、`interjection_removed`、`interjection_trimmed`、`interjection_restored`；关闭“语气词”时删除整条并统计`interjection_removed`，句首/句末被清理则统计`interjection_trimmed`；开启时保留整条，但参考中不存在的仍删除；`review_decision='included'`的手动条目不受影响。旧`interjection_excluded`字段保留为0，仅用于兼容旧前端。碎片检测依据完整词跨界、共同原句或同句相邻可靠参考，遵守用户停顿阈值、宽度、手动分段及导出边界；未能自动合并的才标记，不改文字和时间。校准返回`merged`为自动合并次数，与`merge_suggestions`分开统计。前端把碎片文字和“建议合并”徽标显示为红色，按连续选择≤5000条分请求，分批成功后统一应用，不碰未选邻条。用户勾选两条或多条连续字幕点“合并”时，前端按原顺序拼接文字，时间取第一条开始到最后一条结束，保留全部ASR来源并清除相关建议。分句优先两侧真实词时间；不足时显式估计。仅格式清理不能替无参考/明显异常确认完成。JS的`normalizePunctuation`与Python的`normalize_subtitle_punctuation`统一为只保留问叹语气标点，保护数字/单位/英文词内部符号。

校验显示统一由`cueVerificationIssues()`按阶段判断：内容问题（参考过期、错字/谐音/漏字/多字、无参考、参考中不存在的内容、空字幕）在“校验”和“校准”阶段都显示；版式问题（超过每行字数、建议合并）在“校准”和“对齐”阶段显示；时间问题（对齐失败、词时间异常、时长收紧、无效时间、异常拖长）只在“对齐”阶段显示。问题标签“疑似问题 / 明显问题 / 语气词”三个阶段通用；通过标签只代表最后一次检查，分别是“校验通过 / 校准通过 / 对齐通过”。`computeCueVerification()`负责单条徽标，`verificationStatistics()`按同一规则统计报告（没有执行过任何检查的条目计入“未校验”）。校准只重验本次处理条目；对齐只重验全部字幕的时间与版式，不重跑参考匹配、不改文字、不清“修改完成”。标签只做标注，不再自动写`exclude_export`；导出仍由手动“关闭导出/不导出”控制，下一阶段会解除旧版本留下的自动排除标记（`releaseVerificationExclusions()`）。随后弹出`verificationReportDialog`，显示处理前后总条数、改动条数以及通过/疑似/明显问题数量；`countChangedCues()`按“文字+起止时间”多重集合逐条核对原条目，拆分或改字都算改动。

`modification_complete`存当前文字与起止时间确认快照；人工修改、拆分合并和校准后显示绿色“修改完成”并隐藏旧警告。确认只覆盖内容：后续对齐或手动调整时间不会作废确认，模型实际改写文字才失效。重新校准或重新校验可清除确认以展示新等级；校准内部刷新缺失/过期参考时保留确认。对齐不再清除确认。原始ASR和旧参考数据继续保存，导出开关独立于校验等级。

### 5.3 模型目录与下载

- **目录**：`data/models/<名称>/`，Whisper 至少需要 `model.bin + config.json + tokenizer.json`（当前 `weights_present` 只检查 `model.bin`，见 R08）
- **国内源**：优先魔搭 ModelScope，其次 HF-Mirror；两源清单均不可用时才尝试 Hugging Face 官方
- **测速**：取真实权重前 256 KiB 做小流量采样，按包含连接时间的样本速度排序；不代表整下载过程最快
- **续传**：临时 `.part` 文件，支持取消重试；续传校验 Content-Range 起点和总长度；完成后检查大小和可用 SHA-256
- **超时**：清单和采样请求 6 秒，文件请求 12 秒
- **源固定**：魔搭按提交版本固定链接；HF 镜像按仓库提交版本固定；备用文件必须名称、大小、SHA-256 三者相同才允许加入
- **独立环境**：FireRed/Qwen 依赖安装到 `data/engines/<引擎>`，子进程调用；依赖清单、导入自检和安装源在 `config/engines.json`，源码优先阿里云 PyPI 镜像并逐源回退；pip 缓存在 `data/cache/pip`；FireRed SDK 取官方 GitHub 源码
- **GPU**：随附 `torch.mode = manual`，下载模型/配置环境只装 CPU 版 torch，不下载 CUDA；检测到 NVIDIA 显卡时界面提供“下载 GPU 环境 · 约 2.9 GB”，显式点击后才通过 `POST /api/runtime/gpu` 给 qwen/firered 补装 cu126 版 PyTorch，`ready.json` 记录实测 torch 版本和 `cuda_available`。安装/驱动失败恢复 CPU 并记 `gpu_error`，可重试或继续用 CPU。Whisper 的 CTranslate2 需要系统级 cuBLAS/cuDNN DLL 才能用 GPU，否则自动回退 CPU

### 5.4 模型体积参考

三个主模型加 ForcedAligner 合计约 **12 GB**（按下载体积估算，不含独立引擎的 Torch 等运行时）。`.venv` 本身约 345 MB，主要是 PyAV、CTranslate2、NumPy、ONNX Runtime、jieba 的 DLL/词典。

## 8. 启动入口（run.bat）

`run.bat` 是唯一启动入口（原中文入口仅转调 run，已移除；安装检查和后台启动均由 run 调度）。流程：

1. **虚拟环境优先**：已有可用 `.venv` 时直接使用，不要求另一个系统 Python 在 PATH 中
2. **虚拟环境检查**：不可用时改名保留为 `.venv.broken_*`，再创建新环境，不直接删除旧环境
3. **创建虚拟环境**：`.venv` 不存在时用包内 `runtime\python\python.exe -m venv .venv`
4. **逐项检查**：`tools/bootstrap.py` 依次检查便携 Python、`.venv`、pip、运行依赖、程序文件、数据目录；每项通过显示“通过”，缺失显示“缺失 … 正在补全”，先尝试包内 `wheels\` 离线安装，失败或没有 wheel 时再按国内镜像联网安装。控制台常驻一行进度条（包数或下载百分比 + 当前包名），完整 pip 输出写入 `data/logs/pip.log`，检查摘要写 `data/logs/bootstrap.log`
5. **启动服务**：`backend/launch.py` 用 `pythonw.exe` 启动隐藏服务，重定向输入输出；最多等待30秒，实际检查网页及带令牌的健康接口，失败保留提示和 `launcher.log`
6. **端口**：默认 8765，被占用时自动顺延（实际 bind 失败才顺延，非预先探测）
7. **浏览器**：优先 Chrome/Edge app 窗口，回退默认浏览器
8. **日志**：写 `data/logs/app.log`，程序内"帮助 → 终端"可查看
9. **窗口**：按屏幕降一档居中，2K 屏使用 1920×1080 物理像素，Windows 窗口使用胶片图标和单独任务栏身份

安装和启动共用 `run.bat`。`run.bat --console` 显示前台控制台，Ctrl+C 可停止。请求日志统一使用 logging，兼容 pythonw 下标准错误流为 None；终端日志接口仅增量读取最多256KiB尾部，不记录其自身轮询请求。

## 14. 关键设计约束（给 AI 的注意事项）

1. **文本始终以人工确认为准**：ASR、对齐、匹配都不能自动覆盖人工修改的文字
2. **原始记录不可变**：`asr_original / original_text / original_start / original_end` 只读，人工操作只改当前文本/时间
3. **算法不调用大语言模型**：文本匹配用 RapidFuzz + pypinyin + difflib，不听音频，不判断视频实际说了什么
4. **分数不是识别正确率**：即使综合分 1.0，只要有实质字符差异仍显示疑点
5. **保守策略优先**：边界微调、合并、分段遇到不可靠情况保留原条标 `needs_review`，不强行处理
6. **单 worker 串行**：识别、对齐、下载不并发抢占资源；任务字典去重靠客户端 `request_id`；参考匹配由 `MatchTasks` 单独计进度、可取消并限制 150 秒，不保存大结果
7. **工程保存原子性**：临时文件 + fsync + `os.replace` + 跨进程锁 + revision 冲突检查，但不保证强杀进程/断电恢复；前端遇 409 停止重复保存并保留本页修改，通过“备份本页并载入最新工程”显式恢复。识别轮询持续断线时可“停止等待，恢复编辑”，任务标识保留给“继续查询原任务”，避免重复提交
8. **模型不随项目分发**：`data/models/` 为空时识别功能不可用，需自行下载
9. **不合并 requirements**：直接依赖和锁定快照分工不同
10. **legacy 旧程序已清理**：原 `legacy/` 目录已移入回收站，当前运行不依赖它

## 15. 启动、依赖与运行环境设计

本章记录**为什么这样设计**和**改动时必须守住的约束**，实现细节以代码为准。

### 15.1 目录分层

| 路径 | 内容 | 打包 | 可删除 | 说明 |
|---|---|---|---|---|
| `data/models/<模型>/` | 模型权重、`.part` 片段、`.studio-model.json` | 否 | 是（需重新下载） | 只放权重，不放 Python 包 |
| `data/engines/<引擎>/` | 每个引擎独立的 venv、`install.log`、`ready.json` | 否 | 是（重新配置环境） | 版本互相隔离，避免 Torch/Transformers 冲突 |
| `data/cache/pip/` | pip 下载缓存 | 否 | 是 | 主环境和引擎环境共用 |
| `data/projects/`、`data/results/`、`data/uploads/`、`data/outputs/` | 用户工程和素材 | 是 | 否 | 打包保留 |
| `config/engines.json` | 引擎依赖、安装源、GPU 策略 | 是 | 否 | 唯一事实来源 |

**为什么依赖不和模型放一起**：模型目录会被 `weights_present()` 扫描，备份/迁移时按“权重”处理；把 venv 混进去会让体积统计、目录识别和迁移排除都变复杂。依赖在 venv 里，模型是数据，两者生命周期不同。

### 15.2 启动链路

**本机开发**：运行 `py -3.13 dev.py --setup-only`，由 `tools/development.py` 管理 `%USERPROFILE%/.virtualenvs/SubtitleStudio`，使用虚拟环境解释器安装 requirements、应用锁文件约束并执行 `pip check` 和主模块导入检查。`pip --isolated` 忽略全局 pip 配置，子进程环境禁用用户包与安装路径重定向。无法使用的旧开发环境会保留，不自动删除。日常运行 `py main.py`，全局 Python 调用时仅切换到项目虚拟环境，随后直接运行后端源码；不调用便携 bootstrap、不在每次启动时安装依赖。已有虚拟环境内也可直接 `python main.py`。开发不依赖 `runtime/`、`wheels/` 或根目录 BAT。`--background` 可切换后台启动，默认前台运行、Ctrl+C 停止；原 `py dev.py` 仍兼容。环境目录可由开发入口 `--venv` 或环境变量 `SUBTITLESTUDIO_DEV_VENV` 指定。

**便携版**：

```
run.bat
  → 设置 PYTHONUTF8 / PYTHONNOUSERSITE / PIP_CACHE_DIR=<项目>\data\cache\pip
  → 调用 tools\bootstrap.py（中文提示和进度条都在 Python 里，bat 保持纯 ASCII）
  → 依次检查并显示结果：
       便携 Python / .venv / pip / 运行依赖 / 程序文件 / 数据目录
       → 通过：显示“通过”
       → 缺失：显示“缺失 …，正在补全”
            → 有 wheels\*.whl：pip install --no-index --only-binary=:all: --find-links wheels（约 1 分钟）
            → 没有或离线安装失败：按阿里云→清华→中科大→华为云→官方顺序联网安装
       → 常驻一行进度条：[####----] 62% 8.2/13.4 MB 当前包名
       → 完整输出写 data/logs/pip.log，检查摘要写 data/logs/bootstrap.log
  → 全部检查通过后直接打开界面
  → .venv\Scripts\python.exe backend\launch.py [参数]
       → 已有实例：打印“已在运行”，打开浏览器后立即返回
       → 没有实例：用 pythonw.exe 后台启动 backend\app.py
       → 轮询就绪文件 + /api/health（带会话 token）
       → 成功打印地址后立即退出，控制台关闭（不倒计时）
       → 失败写 data/logs/startup-error.txt 并返回 1，控制台暂停显示错误
```

**必须守住的约束**：

1. **`run.bat` 只能有 ASCII 字符，且保持 CRLF**。Windows cmd 在 OEM 代码页下解析批处理，UTF-8 中文注释可能吞掉换行，导致命令片段被当成指令执行。需要中文提示就写到 Python 里。
2. **不要恢复 VBS 启动器**。用户要求只有一个入口文件；隐藏控制台由 `launch.py` + `pythonw.exe` + `CREATE_NO_WINDOW` 完成。
3. **不要重新打开 `SO_REUSEADDR`**。Windows 上它允许多个进程绑定同一端口，重复双击会悄悄堆出多个后台服务。`StudioHTTPServer.allow_reuse_address = os.name != "nt"` 是单实例安全的前提。
4. **实例地址写 `data/run/instance.json`**。启动器优先读它，避免逐端口探测；只有状态文件缺失时才扫描附近 6 个端口。
5. **检查全部通过后立即退出并关闭控制台，不倒计时**；失败时 `run.bat` 暂停窗口，必须保留错误提示。
6. `--console` 是排障入口：前台运行 `app.py`，日志直接进控制台。`--no-browser` 只影响是否打开浏览器。

**离线依赖**：`wheels\` 由 `tools/prepare_wheels.py` 按 `requirements-lock.txt` 生成；锁文件包含全部传递依赖，`pip wheel --prefer-binary` 会下载现成 wheel，并为没有 wheel 的 jieba 现场构建。生成后用 `pip install --dry-run --ignore-installed --no-index --only-binary=:all: --find-links wheels -r requirements.txt` 验证这套 wheel 能独立装完运行依赖。requirements 变化后必须重跑；脚本用清单哈希判断是否过期。发布包因此增加约 110 MB，但接收方首次启动不再依赖网络和镜像回退。首次启动与打包下载共用 `tools/pip_progress.py` 的一行总进度条；离线→联网的回退在 `bootstrap.py` 内部完成，失败返回非零，由 `run.bat` 暂停窗口显示错误。

`app.py` 写 `data/logs/app.log`；`/api/health` 返回 `ok`、`version`、`models`、`auxiliary`、`data_dir`、`uptime`、`port`、`log_file`；`/api/logs` 提供日志尾部。帮助对话框顶部显示软件名、当前版本（优先取 `/api/health`）、作者邮箱 `weieouer@gmail.com` 和“未经授权不得商用”声明。轮询日志和任务接口不写访问日志，避免刷屏。文件/目录选择框走 Windows 原生 `GetOpenFileNameW` / Shell API，不依赖 Tcl/Tk（随包 runtime 不含 tkinter）。

### 15.3 模型下载

- 模型清单在 `backend/core/model_manager.py` 的 `CATALOG` / `AUXILIARY`；未知名字一律拒绝，不允许下载任意 URL。
- 下载目标固定为 `data/models/<name>`，支持历史别名（`MODEL_FOLDER_ALIASES`）。目录名和清单名不一致时按以下顺序找：手动指定目录（`data/models/.locations.json`）→ 清单名与别名 → 名称包含匹配（最长匹配优先）→ 回退下载目标。
- 手动指定走 `POST /api/models/locate`：`{"model":"large-v3","path":"D:/模型/自定义目录"}`，`path` 为空表示恢复默认。目录里必须有 `model.bin` / `model.safetensors` 等权重文件，否则返回 400。这层映射只影响读取位置，不改文件、不复制权重。
- 文件先写 `.part`，用 `Range` 续传；校验 `Content-Range` 起点和总长度；有 SHA-256 就校验；完成后原子替换。
- 多源：ModelScope → HF-Mirror → Hugging Face 官方，短采样测速排序（`core/model_sources.py`）。
- 完成后写 `.studio-model.json`（仓库、revision、来源、文件大小和哈希）；下载过程中有 `.studio-downloading` 标记；取消保留片段，下次继续。
- 每次下载或配置环境时，`ModelDownloads` 把状态写入 `data/run/activity.json`，`backend/core/progress_console.py` 用 `CREATE_NEW_CONSOLE` 另开一个可见控制台窗口，实时显示进度条、速度、已用/剩余时间和 `data/engines/*/install.log` 的 pip 安装输出；任务完成、失败或取消后窗口自动关闭。关闭窗口不影响后台任务，界面里仍有同样的进度。

### 15.4 引擎隔离环境

每个引擎一个 venv：`data/engines/<engine>`，通过 `engine_runner.py` 子进程调用，主 `.venv` 不装 Torch/Transformers。

安装流程（`ModelDownloads._prepare`）：

1. `runtime_ready(engine)` 为真则直接返回。
2. 创建 venv（`with_pip=True`）。
3. 若该引擎声明了 `torch: true`：按 `desired_torch()` 选择 CPU 或 CUDA 版 `torch`/`torchaudio`（见 15.6）。默认 `manual` 只装 CPU，不自动下载 CUDA；CUDA 安装失败或实测不可用会恢复 CPU 版后再继续。
4. 按 `indexes` 顺序安装引擎包，任一源成功即停止；所有 pip 子进程共享 `PIP_CACHE_DIR`。内置顺序：阿里云 → 清华 → 中科大 → 华为云 → 腾讯云 → PyPI 官方。
   - 换源只解决“镜像不可用”。解析冲突换源同样失败，应改 `packages` 里的版本约束。
   - Qwen 必须同时装 `gradio<6`：`qwen-asr==0.0.6` 不带上限，而 gradio 6.x 要求 `huggingface-hub>=1.0`，与 `transformers==4.57.6` 的 `<1.0` 冲突；不加时 pip 会逐个回退 6.30、6.29……每次下载约 30 MB，看起来像卡住。
   - `qwen-asr` 元数据没声明 `torch`，但代码顶部 `import torch`；实际由 `accelerate==1.12.0` 带入 PyTorch（Windows 上 PyPI 的 torch 即 CPU 版）。
   - **中文路径限制**：`nagisa` 用 DyNet 读模型，项目路径含中文时必定失败。`patch_nagisa_model_path()` 在 pip 安装后、导入自检前把模型复制到 `%PUBLIC%\SubtitleStudio\nagisa\` 并改写引擎 venv 里的 `nagisa/tagger.py`；纯英文路径下不做改动，重装依赖后会重新应用。若 `%PUBLIC%` 也含中文，自检失败信息会提示把项目移到纯英文目录。
5. 用配置里的 `probe` 做导入自检，失败则不写就绪标记。
6. 写 `ready.json`：`engine`、`packages`、`indexes`、`torch`（实际装的是 `cuda` 还是 `cpu`）、`cuda_available`（实际导入 torch 后的实测布尔值）、`prepared`；GPU 安装失败且已恢复 CPU 时另写 `gpu_error`。

`runtime_ready()` 的语义：`whisper` / `builtin` 永远就绪；其他引擎必须同时存在 venv 的 Python 和 `ready.json`；如果引擎声明 `torch: true` 且 `desired_torch() == "cuda"`，还要求 `ready.json.torch == "cuda"`，这样把 `torch.mode` 改成 `cuda` 后旧 CPU 环境会被视为未就绪，下次“配置环境”自动补装。反过来期望 CPU、或期望 CUDA 但已记录 `gpu_error` 的可用 CPU 环境都算就绪，不会反复尝试 2.9 GB 下载。`engine_gpu_ready()` 只认 `ready.json.torch == "cuda"`；当前驱动是否真能调到显卡由 `engine_runner` 启动时再次实测 `torch.cuda.is_available()`，显式 `cuda` 不可用会报错并提示改选 CPU/自动。取消时终止 pip 子进程，保留 pip 缓存。

### 15.5 `config/engines.json` 契约

```json
{
  "version": 1,
  "pip_cache": "data/cache/pip",
  "indexes": ["镜像1", "镜像2", "官方"],
  "torch": {
    "mode": "auto",
    "cuda_index": "https://download.pytorch.org/whl/cu126",
    "packages": ["torch", "torchaudio"]
  },
  "engines": {
    "qwen": {
      "packages": ["qwen-asr==0.0.6", "gradio<6"],
      "probe": "from qwen_asr import Qwen3ASRModel, Qwen3ForcedAligner",
      "torch": true
    }
  }
}
```

| 字段 | 作用 | 非法时的行为 |
|---|---|---|
| `pip_cache` | pip 缓存目录，相对路径按项目根解析 | 回退 `data/cache/pip` |
| `indexes` | 全局 PyPI 源，按顺序回退 | 回退内置六个源 |
| `torch.mode` | `manual`（默认，只装 CPU，GPU 由按钮显式安装） / `auto` / `cpu` / `cuda` | 回退 `manual` |
| `torch.cuda_index` | CUDA 版 torch 的索引 | 回退官方 cu126 |
| `torch.packages` | 预装的 CUDA 包 | 回退 `torch`、`torchaudio` |
| `engines.<name>.packages` | 该引擎的 pip 参数 | 回退内置声明 |
| `engines.<name>.probe` | 导入自检语句 | 回退内置语句 |
| `engines.<name>.indexes` | 覆盖全局源 | 回退全局 `indexes` |
| `engines.<name>.torch` | 该引擎是否使用 GPU 版 torch | 回退内置值 |

- 配置按“路径 + mtime”缓存，改文件后无需重启即可影响下一次安装；`RUNTIME_PACKAGES` / `RUNTIME_INDEXES` 只是导入时快照，新代码不要在运行时依赖它们。
- 只允许内置的三个引擎名；新增引擎不能只改 JSON，还要在 `CATALOG`、`engine_runner.py`、`asr.py`/`external_asr.py` 增加调用逻辑。
- 安装源必须是完整的 pip `--index-url`（simple 索引）。阿里云的 `pytorch-wheels` 是文件列表页，不能直接填 `cuda_index`。

### 15.6 GPU 设计（默认只准备，不下载）

GPU 有三层，必须同时满足：引擎 venv 里装的是 CUDA 版 torch，`torch.cuda.is_available()` 实测为真，且界面“设备”选 `auto` 或 `cuda`；`cpu` 即使装了 CUDA torch 也按 CPU 跑。

- **默认 `torch.mode = manual`**：`desired_torch()` 返回 `cpu`，下载模型/配置环境只装 CPU 版 torch，不会自动下载 CUDA。`cpu` 同样强制 CPU；`auto` 检测到 NVIDIA 显卡才随配置装 CUDA；`cuda` 强制。显卡检测用 `nvidia-smi --query-gpu=name`，进程内缓存一次。
- **一键安装**：检测到 NVIDIA 显卡时，前端在“设备”下方显示“下载 GPU 环境 · 约 2.9 GB”。点击调用 `POST /api/runtime/gpu`，后端 `start_gpu()` 只对已准备好的 qwen/firered 环境补装 CUDA torch，进度与模型下载共用 `/api/models/download`。没有已配置的 torch 引擎时返回中文提示，要求先下载 Qwen/FireRed 模型。
- **安装与验证**：先用 `torch.cuda_index`（cu126）单独装 `torch`/`torchaudio`，始终带 `--upgrade --force-reinstall`，避免 CPU torch 已存在时 pip 报 `already satisfied` 却误标 GPU；再从普通镜像装引擎包。装完在引擎 venv 里执行 `import torch; print('cuda' if torch.cuda.is_available() else 'cpu')` 实测，并做一次引擎导入自检；`ready.json` 记 `torch`、`cuda_available`，两者都通过才算 GPU 就绪。
- **失败回退**：CUDA 下载失败、实测不可用或引擎无法在 CUDA 环境加载时，自动重装 CPU 版 torch，`ready.json` 写 `gpu_error`，界面显示“GPU 安装失败，已回退 CPU”，可重试或继续用 CPU。`runtime_ready()` 承认带 `gpu_error` 的 CPU 环境就绪，避免每次启动重试 2.9 GB；`engine_gpu_ready()` 只认 `ready.json.torch == "cuda"`，设备选 `GPU (CUDA)` 而环境未就绪时后端直接给出中文提示，真正启动引擎时还会再实测一次显卡，不会假装在用 GPU。
- **状态接口**：`gpu_status()` 随 `/api/health`、`/api/models` 返回 `mode`、`nvidia`、`state`（`cuda` / `partial` / `failed` / `cpu` / `missing`）、`downloadable`、`size_hint`、`error` 和逐引擎状态；该函数只读文件，不触发安装。界面按状态显示“下载 GPU 环境”“补全 GPU 环境”“重新安装 GPU 环境”或当前 CPU 状态。
- CUDA 版 torch 首次约 2.9 GB，之后走 `data/cache/pip`。取消安装会保留已完成的引擎和 pip 缓存。
- 引擎差异：qwen（ASR 与 ForcedAligner）和 firered（模型推理）都走 torch，装 CUDA torch 收益最大。
- **Whisper 不走引擎 venv 的 torch**：它用 faster-whisper/CTranslate2。要用 GPU，系统必须能加载 CUDA 12 的 `cublas64_12.dll` 和 cuDNN 9 的 `cudnn64_9.dll`；`asr._cuda_runtime_ok()` 检查 cuBLAS，缺失时 `auto` 自动回退 CPU。给 Whisper 开 GPU 需要把 `nvidia-cublas-cu12`、`nvidia-cudnn-cu12` 装进主 `.venv` 并引导 DLL 路径，是独立后续工作。
- 4060 8GB 跑 Qwen 0.6B 对齐或 1.7B ASR 单任务没问题；不要假设大模型和辅助模型能同时常驻显存。

### 15.7 打包

开发环境位于项目外，也不会打入 ZIP。源码根目录没有 BAT；`selected_files()` 将 `tools/portable/run.bat` 发布模板映射为包内根目录 `run.bat`，继续作为接收方便携版启动入口。源码运行、环境管理和便携配置已分开；`tools/bootstrap.py` 仅服务发布后的首次启动。日常 `py build.py --output <项目外ZIP路径>` 先用开发环境准备/检查 wheels，再调用原打包工具；低层 `tools/package_release.py` 仍可独立使用。模板保持 ASCII/CRLF。源码的 `main.py`、`dev.py`、`build.py` 与工具设置随源码保留。纯源码检出后，运行程序只需安装开发依赖；生成便携 ZIP 还需恢复发布资源 `runtime`/`wheels`，它们不提交到 Git。当前维护与交付以便携式 ZIP 为准。

发布工具为 `tools/package_release.py --output <桌面ZIP路径>`。发布包保留便携 Python、程序、文档/验证、依赖声明、引擎配置、当前界面参数和离线依赖 `wheels\`；排除模型、虚拟环境、引擎环境、缓存、日志、进程状态、旧目录记忆和 Python 缓存。`--include-work` 可带工程/结果/项目内素材/导出，但绝对工程路径需在新设备重新关联。缺少 wheel 时默认拒绝打包，确需联网包可加 `--allow-online`。`PACKAGE_MANIFEST.json` 记录实际内容、大小、SHA256、`offline_install` 和 wheel 数量；打包后检查哈希、ZIP CRC、必需文件和排除目录。仅只读打包，不删除或搬动本机模型与依赖。

当前打包入口为 `py build.py --output <项目外ZIP路径>`：固定使用外部开发虚拟环境检查/准备 wheels，再调用原 ZIP 选档与校验流程，不依赖桌面 BAT 或项目内 .venv。首次准备 wheel 需要网络，之后可用缓存；接收方仍优先使用包内 wheels 离线安装。
