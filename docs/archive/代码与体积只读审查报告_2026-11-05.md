# 字幕工作室：代码与体积只读审查报告

审查日期：2026-11-05。对象：当前本地 `SubtitleStudio` 项目。

本轮只新增本报告，没有修改业务代码、依赖、配置或其他文档，没有删除文件、启动识别或下载模型。以源码审查、目录统计、已安装依赖元数据检查为主；少量缺陷通过提取原函数在内存中复现，未生成业务数据。没有运行会覆盖既有验证记录的测试脚本。

## 1. 主要结论

1. **300 多 MB 主要是依赖库。** 当前 `.venv` 为 **345.576 MB / 329.567 MiB**；其中大部分是音视频解码和推理的 DLL、扩展模块、词典，不是前后端源码。
2. **本次扫描的完整目录已约 442.096 MB / 421.616 MiB**，另有 **93.323 MB 的未完成模型下载片段**。看到“300 多 MB”与本次完整目录统计不同，可能来自单位、统计范围或下载进度变化。
3. 前后端实际源码合计仅 **331,497 字节，约 0.331 MB**。目录体积不是由“大量无效业务代码”造成的。
4. 代码已有本地访问校验、原子保存、工程版本冲突保护、下载续传校验、异步结果过期保护等有效基础；但仍发现 **4 项 P1、9 项 P2、2 项 P3**，不能把既有测试通过等同于不存在缺陷。
5. **下一轮应先处理字幕数据完整性和编辑状态，再继续扩展模型或界面。** 本轮仅记录，不实施修复。

## 5. P1 问题详情

### R01：Esc 取消编辑破坏字幕数组

**位置：** `frontend/js/app.js:1409`、`:1411`、`:2401`。

`snapshot()` 现在返回 `{cues, subtitleFile}` 的 JSON 对象，普通撤销使用 `restoreSnapshot()` 正确恢复；但字幕文字框的 Esc 分支仍使用：

```javascript
state.cues = JSON.parse(state.editBefore);
```

这会把整个对象放进 `state.cues`。下一步表格渲染调用 `.map()` 时抛错，后续保存和编辑也可能失败。

**内存复现：** 编辑前设置真实 `snapshot()`，触发原 keydown 处理器的 Escape 分支；`Array.isArray(state.cues)` 变成 `false`，数组渲染出现 `map is not a function`。

**建议：** 所有恢复入口统一走同一快照接口，并补“编辑 → Esc → 继续编辑/保存”的交互回归。

### R02：短字幕时间被自动修改

**位置：** `frontend/js/app.js:1381`，尤其 `:1390`。

`normalizeCue()` 对所有字幕执行 `end >= start + 0.05`。这不是只补非法值，而是会修改合法的短字幕；导入、恢复工程以及接收强制对齐结果都经过该函数。

**内存复现：** 输入 `start=0, end=0.010`，输出当前 `end=0.050`，原始字段仍是 `original_end=0.010`。

**影响：** 当前时间与导入/后端对齐结果不一致，可能与下一条重叠或越过媒体末尾。这违反保留合法原时间的预期。

**建议：** 原样保留合法时间，仅对确实无效的输入给出提示；手动创建字幕的默认长度与导入校验分开处理。

### R03：合并后丢失后一条原始 ASR 记录

**位置：** `backend/core/segment.py:284`。

`merge_cues()` 只在第一条字幕的浅拷贝上拼接当前文本、扩展结束时间，未把第二条的 `asr_original`、`original_text`、`original_start/end` 合并为可追溯来源列表。

**内存复现：** 合并两条分别带 `raw first`、`raw second` 原始记录的字幕，结果当前文本包含两条，原始记录只剩 `raw first`。

**影响：** 合并后的工程无法完整逐条追溯第二条原 ASR；“保留原文”操作可能只恢复第一条内容。原始任务 JSON 或撤销历史可能还含旧数据，但不能代替合并后的可靠来源记录。

**建议：** 使用不可变的原始 ASR 集合，编辑字幕保存来源 ID/范围列表；合并、拆分只改变当前编辑层。

### R04：更换剧本后撤销可恢复旧建议并采用

**位置：** `frontend/js/app.js:1051`、`:1409`、`:1425`、`:1595`。

导入新剧本会清空当前字幕的建议，但不会清理或区分旧历史。历史快照只保存字幕与 SRT 文件，不保存剧本文档/版本。撤销后可以恢复旧剧本的 `reference_match` 和 `script_text`；采用时仅检查 stale、候选确认和叙述标记，没有验证建议所属剧本。

**内存复现：** 保存剧本 A 的快照，导入 B，撤销并执行真实 `applyScript()`：当前剧本仍为 B，采用的文字却为 `reference A`。

**建议：** 给匹配结果绑定剧本文档指纹和字幕版本；更换剧本与撤销必须有明确的历史边界，采用前再次校验上下文。

## 6. P2 问题详情

### R05：编辑派生状态未统一失效

**位置：** `backend/core/segment.py:176`、`:263`、`:284`；`frontend/js/app.js:1450`、`:1715`、`:2350` 附近。

分段清空了旧 `script_text`，却通过浅拷贝保留 `reference_match`、`alignment` 等记录。合并也没有统一清理这些字段；时间拖动/手动修改没有统一将对齐记录置为过期。底部“已对齐”只检查 alignment 存在、未标 stale 和时长为正。

合并内存复现中，合并后的整句仍带第一条的 `high/stale=false` 参考和对齐记录；第二条的 `is_noise` 也没有合并。第二条只有疑似噪音标记、没有其他复核标记时，疑似统计可能漏计。

**建议：** 定义统一的“文本变化、时间变化、结构变化”失效规则，清理或重算匹配、对齐、置信标记和来源元数据。不能仅修改当前文本。

### R06：标准化字簇边界存在假高度匹配

**位置：** `backend/core/reference_match.py:46`、`:125`、`:178`、`:351`。

标准化保存了一对多字符的位置映射，但候选起止允许落在同一原字符展开结果的内部。评分针对截取后的标准化子串，展示原文却回带完整原字符，两者可能不同。

**真实算法复现：** ASR 为 `i`，剧本为连字 `ﬃ`（U+FB03，NFKC 后为 `ffi`）。输出 `high`、综合分 `1.0`，参考原文却为完整 `ﬃ`。这不是完整内容相等。

**建议：** 候选和多条边界必须落在原字簇边界上；评分应与实际展示/可采用原文重新标准化后的内容一致。该问题常见度低于中文错字场景，但位置保真约束要求处理。

### R07：多服务下载会共享文件但不共享锁

**位置：** `backend/core/model_manager.py:74`、`:123`、`:186`；`backend/app.py:707`。

下载锁、取消状态与任务启动锁均在进程内。启动器允许端口递增，因此同时运行两个后端是实际可发生的；两个服务却共用相同模型目录、`.part`、下载标记和引擎虚拟环境。

**影响：** 同模型并发下载可能交错追加、重命名失败或反复校验失败；同引擎初始化也可能争写环境。工程保存已有跨进程锁，模型流程没有同等保护。

**建议：** 每个模型目录、引擎环境使用跨进程锁，或明确限制为单个应用实例。本轮没有启动并发下载验证，以免损坏正在保留的片段。

### R08：就绪判断不足以证明可加载

**位置：** `backend/core/asr.py:17`；`backend/core/model_manager.py:45`、`:49`。

Whisper 发现逻辑主要依赖 `model.bin` 存在，未检查必需配置/分词文件是否齐全；外部引擎的 runtime_ready 只检查 Python 可执行文件和 ready.json。文件被移动、环境升级或初始化标记过期时，界面仍可能允许启动，直到真实加载才失败。

**建议：** 为每个引擎定义最小文件集合、运行环境指纹与轻量导入检查。下载期哈希校验应保留，但不应把存在性检查描述为完整运行验证。

### R09：下载失败兜底与“最快”存在边界

**位置：** `backend/core/model_sources.py:85`；`backend/core/model_manager.py:123`。

官方源只在两个国内源的**清单**都不可用时加入。如果清单正常但权重均无法下载，或者某配置文件没有经过同哈希验证的备用链接，三次重试后会失败，不会重新发现官方备用。两个国内源的采样都失败时，代码仍会从清单可用者中选一个。

测速只读取最多 256 KiB，包含连接开销；下载中不会因持续低速重新测速。urllib 的 timeout 是阻塞操作超时，也不是整个下载的总时限，不能保证所有阶段都在 6/12 秒内结束。

**建议：** 把清单可用、权重可用、持续速度分别记录；文件失败后可安全补查其他源，但续传仍应严格验证相同内容。界面和报告不承诺任何网络下绝对最快。

### R10：续传空间预算偏大

**位置：** `backend/core/model_manager.py:221`。

remaining 只扣除已正式存在的目标文件大小，没有扣除合法 `.part`。当大模型已经下载了大部分、剩余磁盘只够补齐片段及安全余量时，重试仍可能按整文件需求拒绝续传。

**建议：** 依据已经验证的文件版本和部分文件长度计算剩余增量，同时保留校验失败重下与环境安装的空间预留。不能直接无条件扣掉任何同名片段。

### R11：大输入的资源与响应边界不足

**位置：** `backend/core/media.py:208`；`backend/core/reference_match.py:153`、`:268`；`backend/app.py:535`；`frontend/js/app.js` 的表格和侧栏全量渲染。

- ASR/对齐解码先收集所有音频数组，再 `np.concatenate`；1 小时 16 kHz float32 单声道约 230.4 MB，仅拼接瞬间原分块加新数组就可能接近两份，不含模型。外部引擎还把所有块写为临时 WAV。
- 全文匹配允许 50 万剧本文字和 5000 条字幕，组合查询需要多次全局模糊搜索、候选评分与束搜索；接口同步返回，没有匹配任务取消或进度。前端 180 秒请求超时后，后端计算可能仍继续。
- 表格、右侧每条对照及最多 60 个完整 JSON 历史快照，都会随字幕/参考元数据增长；现有 API 还允许一般字幕数组最多 10 万条，不代表 UI 能流畅处理该规模。

**建议：** 为实际目标集数和时长定义并实测上限；音频分块/映射读取、匹配独立可取消任务、虚拟列表和增量历史按需要逐步引入。本轮未执行压力测试，不能给出未经测量的耗时承诺。

### R12：外部模型环境与验证不足

**位置：** `backend/core/model_manager.py:33`、`:186`；`backend/engine_runner.py`。

主环境直接依赖有固定版本，但传递依赖未整体锁定；外部环境还有未固定的 Torch、torchaudio、soundfile、huggingface_hub、FunASR 范围版本，以及 FireRed 的可变化 main.zip。不同日期安装可能得到不同组合。CPU/CUDA 包的选择也没有独立的依赖方案。

现有浏览器任务使用 fake_transcribe/fake_align，不能证明 FireRed、Qwen、Paraformer 与 ForcedAligner 的真实接口、设备与时间戳行为都可用。当前目录也没有完整权重支持本轮实际加载测试。

**建议：** 保存验证过的依赖锁定/SDK 提交与环境指纹，分别验证 CPU、可用 CUDA 和至少一段真实语音。不把安装成功标记当作真实推理验收。

### R13：非中文强制对齐未打通语言配置

**位置：** `backend/engine_runner.py:28`；`backend/core/asr.py:121`、`:128`。

ASR 允许自动识别语言，但 ForcedAligner 调用固定 `language='Chinese'`；Whisper 也固定了普通话简体对白提示。对于纯英文或其他语言素材，不能据此把“多语言识别支持”扩大解释为“多语言提取、校验、对齐全流程均已正确适配”。

**建议：** 将自动识别结果/用户选择的语言沿任务链传递，并针对混合语言说明边界。非中文的实际影响仍需对应 SDK 与语音样本验证，本轮没有把它报告成已发生的识别失败。

## 7. P3 问题详情

### R14：旧入口和旧模型测试残留

**位置：** `setup.bat:37`、`tests/asr_smoke.py:26`。

安装结束提示仍写“双击 start.bat”，当前实际入口是 run.bat。模型冒烟脚本仍硬编码 medium，而当前主要模型列表已换成五个模型；只下载新列表模型时，该脚本不能直接用于相应模型验收。

**建议：** 后续统一启动提示与冒烟脚本的模型参数。这些文件体积极小，属于维护残留，不是 300 MB 来源。

### R15：高度匹配阈值为无可见作用的参数

**位置：** `backend/core/reference_match.py:253`、`:362`；前端匹配参数区。

high 参数只参与参数范围校验和输出 above_high_threshold；高度匹配状态实际上由标准化文本完全相等决定，前端没有使用 above_high_threshold。因此调整界面的“高度匹配”阈值，并不会改变可见的高匹配状态。最低分、拼音门槛和候选分差等参数并非都失效。

**建议：** 要么明确为独立的“高分参考”提示并在 UI 消费，要么取消这个无实际效果的配置。不要为让参数生效而把所有高分错字自动判为正确。

## 8. 保留优点与其他维护事项

值得保留：

- 服务只绑定本机，校验 Host、Origin、会话 Token，跨站请求受限；未看到本轮新增的直接 shell 字符串拼接执行路径。
- 静态文件限制在前端目录，上传文件名处理、JSON 类型/数值检查、媒体 Range 响应均有专门逻辑。
- 工程采用原子 JSON 替换、版本冲突检查和跨进程文件锁，异步结果具有素材代次/快照保护。
- 模型目录固定，权重流式校验，续传检查 Content-Range；文本匹配不隐式调用大语言模型，不自动覆盖 ASR。
- 文本差异展示普遍转义 HTML，原文、参考位置和人工采用动作已有明确的数据字段。

这些是源码检查得到的保护措施，不是完整渗透测试结论，也不保证所有输入组合都安全。

其他维护债务：

- 主控制器职责过多，适合在行为稳定后逐步拆分，不宜现在整文件重写。
- JobManager 的任务字典、结果目录、波形缓存与上传副本没有明确的保留/归档上限，长期使用会增长；应先做可见的占用统计和用户可控清理策略。
- 外部引擎运行日志位于临时目录，失败后目录退出即清理，界面只保留日志尾部，不利于后续完整诊断。
- 项目没有 Git 元数据，历史 ZIP 能保留基线，但不便比较每轮修改；后续可建立版本管理，不能把缓存或用户素材直接全部纳入提交。
