# 字幕工作室复查与环境修复记录

日期：2026-11-04。对象：`字幕工作室/SubtitleStudio` 2.1.0。本文分两部分：先记录本轮虚拟环境故障的定位与修复，再列出通读前后端代码后发现、且此前报告未重点记录的问题与建议。

本次没有改应用代码，只改了 `requirements.txt`（锁定版本）、`setup.bat`（Python 版本检查与坏 venv 自检重建）和 `docs/需求分析.md`（Python 版本）。所有代码问题均为静态审查所得；除环境验证外，未做真实对白和浏览器人工验收。

## 1. 环境故障与修复

### 1.1 根因

`.venv` 是从另一台机器复制来的，`pyvenv.cfg` 指向：

```text
home = C:\Users\admim\AppData\Local\Programs\Python\Python312
version = 3.12.10
```

本机没有这个解释器，只有 `C:\Users\Ouer\AppData\Local\Programs\Python\Python313\python.exe`（3.13.15）。`.venv\Scripts\python.exe` 只是转发到该路径的启动器，所以任何调用都报：

```text
No Python at '"C:\Users\admim\AppData\Local\Programs\Python\Python312\python.exe'
```

结论：这不是依赖装错，而是虚拟环境整体不可用；`pip`、`run.bat`、`setup.bat`（对已有 `.venv` 会跳过创建）都会连带失效。

### 1.2 处理过程

按“先全局安装，再修虚拟环境”的顺序执行：

1. 先确认对应版本可安装：Python 3.13.15 下可解析到
   `faster-whisper==1.2.1`、`av==19.0.2`、`numpy==2.5.4`、`jieba==0.42.1`，
   以及 `ctranslate2==4.8.5`、`onnxruntime==1.31.1`、`flatbuffers==25.12.19`、`protobuf==7.36.2`。
   这 8 个包**没有留在全局**：取包完成后已全部从全局卸载，全局 `numpy` 也还原为原有的 2.5.3。项目依赖只在 `.venv` 内。
2. 将 `requirements.txt` 从最低版本约束改为锁定版本，保证以后 `setup.bat` 装出同一套：

   ```text
   faster-whisper==1.2.1
   av==19.0.2
   numpy==2.5.4
   jieba==0.42.1
   ```

3. 删除旧 `.venv`（目录内只有 `Include/Lib/Scripts/pyvenv.cfg`，无用户数据），用本机 Python 3.13.15 重新创建，升级 pip 到 26.3，再按 `requirements.txt` 安装。
4. 需求分析中的“本机Python3.12.10”已更正为 3.13.15。
5. `setup.bat` 补了前置检查：Python 低于 3.12 直接退出并提示（numpy 2.5.4/av 19.0.2 的 `Requires-Python` 为 `>=3.12`）；执行前先试跑 `.venv\Scripts\python.exe -V`，失败则视为坏 venv 并自动重建，避免再次出现“复制来的环境被跳过创建”。

| 依赖导入 | av 19.0.2 / numpy 2.5.4 / jieba 0.42.1 / ctranslate2 4.8.5 / faster_whisper 1.2.1 / onnxruntime 1.31.1 全部可导入 |

失败的 1 项是 `tests/test_regressions.py:284` 的 `test_job_idempotency_and_light_poll`：它提交 `model="medium"` 的识别任务，而 `backend/app.py:408` 会拒绝未下载模型，响应里没有 `job` 字段。报错本身说明测试依赖本机模型，不是依赖安装问题。

### 1.4 仍需处理：本地模型为空

`data/models/` 是空目录，`/api/health` 的 7 个模型全部 `available:false`。因此：

- 界面“开始识别/提取字幕”不可用；
- 上述后端测试报错；
- `README.md:113` 与需求分析中“已下载 medium、large-v3”的描述与当前副本不符。

如需恢复识别能力，可选其一（约 1.4 GB / 2.9 GB，当前网络实测约 0.6 MB/s，需要一个多小时）：

```bat
.venv\Scripts\python.exe -c "from huggingface_hub import snapshot_download; snapshot_download('Systran/faster-whisper-medium', local_dir='data/models/medium')"
.venv\Scripts\python.exe -c "from huggingface_hub import snapshot_download; snapshot_download('Systran/faster-whisper-large-v3', local_dir='data/models/large-v3')"
```

或者把已有模型目录直接放到 `data/models/<名称>/`（目录里要有 `model.bin`）。在这之前，README/需求分析最好改成“模型需自行准备”，避免误导。

## 2. 代码复查发现

严重度：P1 阻断使用，P2 可见功能/数据问题，P3 体验、健壮性或可维护性。“已记录”指 v2 报告或需求分析已经写明的已知限制，本文不重复展开。

### 2.1 P1

**P1-1 模型目录为空，识别功能整体不可用（环境）。**
位置：`data/models/`、`backend/core/asr.py:17`、`backend/app.py:408`。症状与处理见 1.4。文档与实物不一致这一点，建议在 README 里明确“模型不随项目分发”。

### 2.2 P2

**P2-1 空格键拦截所有按钮的键盘激活。**
位置：`frontend/js/app.js:2411-2422`。
`keydown` 里只把 `input/select/textarea/contenteditable` 视为“正在编辑”，按钮不算；随后 `event.code === "Space"` 直接 `preventDefault()` 并切换视频播放。结果是焦点在“开始识别”“导出 SRT”等按钮上按空格，按钮不会触发，反而播放/暂停视频。键盘用户无法用空格操作任何按钮。

建议：空格分支先排除 `e.target.closest('button, a, [role="button"], summary, label')`，或只在焦点位于 `body`/声波画布时接管空格。

**P2-2 服务断线后识别任务无法放弃，编辑被永久锁定。**
位置：`frontend/js/app.js:1712-1729`、`1780-1786`、`165`。
轮询循环只在拿到 `done/error/cancelled` 或 403/404 时退出；普通网络错误会一直退避重试。此时“取消”按钮走 `/api/jobs/{id}/cancel` 也会失败，`state.jobId` 保持非空，`editLocked()` 持续为真，素材、表格、设置全部锁定。服务不恢复就只能刷新页面。

建议：增加“放弃任务”入口（清空 `jobId`、`asrEpoch`、重试定时器并解锁编辑，提示结果可能丢失），或设置重试上限后自动转入“任务状态未知”而非无限锁定。

**P2-3 发生 409 后，本页自动保存会一直失败。**
位置：`frontend/js/app.js:2036-2049`。
`projectVersions` 只保存服务端返回的新 revision。一旦另一页面先写入导致本页 409，本页的 `expected_revision` 永远停在旧值，之后每次自动保存继续 409；`saveAll()`、关页前保存都无法成功，只能按提示手动 reload 并丢失当前修改。提示语“重新加载工程”没有对应按钮。

建议：检测到 409 时提供两个明确动作——“重新加载服务端版本（放弃本页修改）”和“以本页内容覆盖（先取最新 revision 再提交）”，不要只弹 toast。

**P2-4 光标进出表格单元格就会标脏并触发保存。**
位置：`frontend/js/app.js:2349-2360`。
`focusout` 无论内容是否变化都调用 `scheduleSave()`，而 `scheduleSave` 会 `editRevision++`、`dirty=true` 并排 1.2 秒后的保存。点进任意时间/文字单元格再点走，就产生一次无意义的工程写入和 revision 增长；在 1.2 秒内关页还会弹“未保存”提示。

建议：只在 `state.editBefore && snapshot() !== state.editBefore` 时 `scheduleSave()`；其余情况只清空 `editBefore`。

**P2-5 智能分段会清空词时间，之后再调“停顿断句”不再生效。**
位置：`backend/core/segment.py:181`（分段结果 `"words": []`）、`backend/core/segment.py:205-214`（停顿切分要求 `len(words) >= 2`）。
“智能分段”按宽度切分后每片词的 `words` 都是空数组；用户随后调整停顿阈值再点一次“智能分段”，`split_on_gaps` 因没有词时间而全部跳过，界面看起来像参数没生效。这正是“有词时间时细分、不足时估算”设计的副作用，但文档没有提示不可逆。

建议：分段时把 `_char_times`/词表按切片分配到各片（至少保留每片首尾词时间），或在前端第二次分段时提示“当前字幕无词级时间，停顿断句不会生效”。

### 2.3 P3

| 编号 | 位置 | 问题 | 建议 |
|---|---|---|---|
| P3-1 | `frontend/js/app.js:2404-2409` | 页面隐藏时用 `fetch(..., {keepalive:true})` 兜底保存，但浏览器对 keepalive 请求体有 64 KiB 上限；约 150 条以上字幕的工程会静默失败，`beforeunload` 也不一定触发 | 改用 `navigator.sendBeacon`（同样有限制时先压缩/分片），或缩短自动保存防抖并在 `visibilitychange` 时明确提示保存失败 |
| P3-2 | `backend/core/segment.py:292-297` | “合并短句”只比较角色和间隔，没有比较 `is_noise`，疑似噪音条目可能被合进正常台词 | 合并条件加入 `bool(prev.is_noise) == bool(cue.is_noise)`，或默认跳过噪音条 |
| P3-3 | `backend/core/srt_io.py:26-27` | 编码尝试顺序是 UTF-8 → GB18030 → Big5；GB18030 几乎能解码任意字节，Big5 文件通常在前一步就被误解成乱码，Big5 分支实际很少命中 | 对候选解码结果做可打印字符/常用字评分后取最优，而不是“能解码就采用” |
| P3-4 | `frontend/js/app.js:1350-1355` | `normalizeCue` 把 `end <= start` 的导入字幕静默改成 `start + 0.05`，不提示；用户以为原文件的时间被保留 | 保留原值并标 `needs_review`，或在导入结果里汇总“已修正 N 条零时长字幕” |
| P3-5 | `backend/core/jobs.py:59-63`、`backend/app.py:140-144`、`backend/app.py:601-627` | 任务字典、`data/results/*.json`、`data/uploads/drag/*` 都没有清理策略；长时间使用会持续占磁盘，任务字典只在进程内无限增长 | 启动时按时间/数量清理，或提供“清理缓存”入口并显示占用 |
| P3-6 | `backend/app.py:637-644` | 系统文件对话框 `subprocess.run(timeout=600)` 超时抛 `TimeoutExpired`，落入通用 `except Exception`，返回 500“服务器错误”，用户看不到是选择框超时 | 捕获超时并返回 504/400 的明确提示，必要时结束子进程 |
| P3-7 | `backend/app.py:458-462` | 导出时“选不重名文件”和 `open(..., "x")` 不在同一个跨进程锁里；两个服务实例同时导出可能撞名，第二次抛 `FileExistsError` 变 500 | `open("x")` 失败时递增后缀重试，或把命名和创建放进同一把跨进程锁 |
| P3-8 | `frontend/js/app.js:1246-1247` | `loadMedia` 的入口检查没有 `state.loading`；批量列表快速点两项会并发加载，epoch 能防止结果错配，但会重复保存/探测 | 入口增加 `state.loading` 判断，或在队列点击处禁用 |
| P3-9 | `tests/test_regressions.py:284-296` | 任务幂等测试依赖本机已有 `medium` 模型；干净环境（如当前 `data/models` 为空）必然报错，容易被误判成代码回归 | 用 `patch.object(app, "list_models", return_value=[{"name":"medium","available":True}])` 隔离模型探测 |
| P3-10 | `frontend/js/app.js:2420-2422` | 空格快捷键与按钮语义冲突（同 P2-1）；声波画布的 `role="slider"` 也没有实现上下/左右调整选区的完整键盘路径 | 统一键盘交互规则：控件内交给控件，只有画布/空白处接受全局快捷键 |

### 2.4 本次确认没有问题的点

避免把已经做对的地方再当缺陷：

- 静态文件路径穿越、Host/Origin/会话令牌、Range 单范围解析、请求体大小与类型校验均有实际测试覆盖，本轮复查未发现新的绕过路径。
- 工程保存使用跨进程锁 + 临时文件 + `fsync` + `os.replace`，并做 revision 冲突检查；同进程前端保存也已串行化。
- 表格、剧本建议、队列、模型名等动态内容都经过 `escapeHtml`/`textContent`，未发现明显 XSS 注入点。
- `parse_qs` 之后不再二次 `unquote`，中文/空格/加号路径不会二次解码，与 v2 报告 R-16 一致。

## 3. 建议处理顺序

1. **P1-1**：准备模型或修正 README/需求分析，否则应用只能导入 SRT、不能识别。
2. **P2-1、P2-2、P2-3**：三个都会把用户卡死在界面里（键盘不可用、断线锁定、409 无法保存），优先修。
3. **P2-4、P2-5**：影响日常编辑体验和参数可信度。
4. **P3-1、P3-2、P3-4**：数据可靠性相关，改动小。
5. 其余 P3 可随版本迭代处理；`tests/test_regressions.py` 的模型依赖建议和下一次测试改动一起修。

## 4. 复现命令

```bat
:: 环境自检
.venv\Scripts\python.exe -V
.venv\Scripts\python.exe -m pip list

:: 后端回归（不写 docs/修复验证）
.venv\Scripts\python.exe -m unittest discover -s tests -p "test_*.py" -v

:: 启动服务并检查
.venv\Scripts\python.exe backend\app.py --no-browser --port 8799
```

服务启动后访问 `http://127.0.0.1:8799/`（需要从页面 meta 取会话令牌，直接 curl `/api/health` 会被 403）。
