## 2. 识别、时长与对齐算法

### P0：建立完整的失败处理流程

建议流程：**识别 → 检查文本与粗时间 → 有依据地分句 → 对齐 → 局部重试 → 最终质量检查 → 人工复核**。最终检查必须放在收紧、重叠处理、拆条全部完成之后，避免中间步骤合格、最后结果异常。

1. 对齐前标出字数与跨度严重不相称、粗时间覆盖多个语音段、原词时间不完整的字幕。粗时间不可信时，不直接拿整段跨度当一个可靠锚点。
2. 正常字幕沿用现有按字幕组与静音切窗的逻辑；异常组用相邻可靠字幕限定范围，按语音段建立多个候选，局部重试。不要默认把每一条字幕孤立对齐，也不要只选“声音最大”的区间。
3. 对齐后联合检查词覆盖、首尾位移、异常长词、语音覆盖、相邻顺序和时长异常。时长合理也可能整体贴错位置；语音覆盖高也可能是另一人的声音。
4. 失败分成“沿用可靠原时间”“时间仍不确定”两类。原时间也异常时保留可恢复记录，显示“定位失败”，进入复核列表，不能算对齐通过。
5. 单个零时长词不应轻易废弃整条的其他有效证据。先检查模型时间量化、相邻同时间词和字词映射；允许保守合并同一时间单元，无可靠边界则明确标为估计。不能通过随意插值制造“成功”。优先复现当前 82 条词时间不可用的来源。
6. 每次重试保存输入、模型输出、最终结果和失败原因；采用新结果前验证工程、文本和时间版本，防止覆盖刚完成的手工编辑。

现有实现依据：[alignment.py](../backend/core/alignment.py)、[audio_boundaries.py](../backend/core/audio_boundaries.py)、[jobs.py](../backend/core/jobs.py)。当前最大分组跨度约 230 秒；Qwen 官方说明对齐支持最多 5 分钟音频，因此“超过官方最大时长”不能直接解释本项目这些异常。对异常组缩窗是待对照验证的策略。[Qwen 官方说明](https://github.com/QwenLM/Qwen3-ASR)

### P1：降低音效和识别错误的影响

| 改进 | 实施方式 | 取舍 |
|---|---|---|
| “仅人声”改名 | 改为“语音活动检测”，提示仍可能保留配乐、笑声和重叠对白 | 避免让用户误以为已经做人声分离 |
| 识别语言与场景 | 提供“普通话 / 自动”等选项；不把普通话短剧提示固定用于所有素材 | 先用同一批样本对照，保留自动模式 |
| 疑难片段重识别 | 从所选字幕附近取有上下文的音频；可换模型，显示文字和时间差异，由用户采用 | 先处理异常片段，避免整片多模型重复跑 |
| 外部引擎分块 | 当前 25 秒硬切改为优先选静音/完整语音边界；需要重叠时记录映射并去重 | 不能靠拼接字符串去重，重复台词会误删 |
| Qwen 时间戳 | 现有 Qwen ASR 分支只读文字，起止使用整块范围；评估接入官方 ASR＋对齐时间戳接口 | 需要对齐模型与额外计算，不能宣传 ASR 自带精确词时间 |
| 参考剧本 | 人名、术语和上下文作辅助；歧义、低分、剧本外台词不自动替换 | 参考相似度不代表音频实际说了这句 |
| 非人声误识别 | 综合无语音分数、重复、词时间、VAD 标记“疑似非对白”，允许试听和恢复 | 不仅凭一个分数删除轻声对白 |
| 人声分离 | 放在“疑难音频增强”可选项，保存原音频；比较增强前后再采用 | 分离可能损失轻声、尾音，且增加耗时和模型体积 |

Qwen 官方提供配合 ForcedAligner 的 `return_time_stamps=True` 用法；应先核对本机锁定 SDK 的兼容性。[官方示例](https://github.com/QwenLM/Qwen3-ASR#usage) Silero 的定位是语音活动检测；它不是台词内容校验器，也不是人声分离器，这一界面边界是基于其用途和本项目调用方式作出的判断。[Silero 官方说明](https://github.com/snakers4/silero-vad)

### P1：区分“字太多”和“停得太久”

- 字数过多：按句意、标点、完整词和可靠停顿拆条。复查确认当前后端分段和前端检查都按每个非换行字符计 1；界面原有“英文计 0.5”的说明与实现不符，第一批修正说明。是否改为视觉宽度须统一分段、检查、预览与导出后评估。
- 时间过长：先定位真实说话区间，文字很短时不要为了凑时长机械切成多个重复条目。长停顿可拆，持续拖音或慢速对白保留人工例外。
- 字数时长经验值只作异常证据之一。当前后端警戒值与前端偏长判定不是同一套公式，应统一返回原因；不要将这些经验值称为行业标准。
- “最长显示”不能作为修复音轨定位的按钮。建议改成明确的“显示设置预览”，并提供可撤销的“应用到时间轴”；涉及截断发声时只给建议。默认预览、编辑区、最终导出使用同一份已应用时间。
- 需要保留临时预览时，持续显示“预览未应用”；导出弹窗写清使用的时间依据和受影响条数。

## 3. 标签与报告设计

主行最多显示一个最需要处理的问题，加一个人工确认/导出标记；详情展开看各维度，避免堆满徽标。

| 维度 | 推荐标签 | 判定及失效规则 |
|---|---|---|
| 内容 | 待核对、参考一致、内容有差异、文字已确认 | “参考一致”只说明与参考相符；文字变化后人工内容确认失效 |
| 时间 | 未对齐、自动对齐完成、时间待复核、定位失败、时间已确认 | 自动完成表示得到结果；只在时间未变、未拆并时保留人工时间确认 |
| 版式 | 超宽、阅读过快、建议分段 | 共用分段的显示宽度；参数变化后重算 |
| 导出 | 导出、不导出 | 用户明确控制，与勾选、筛选和质量标签独立 |
| 处理过程 | 已分段、已回退、已收紧 | 放详情，不能替代质量结论 |

显示优先级：定位失败/无效时间 → 时间或内容待复核 → 人工确认/自动完成。比如同一条可以同时是“文字已确认”和“时间待复核”，后者必须可见，仍进入待复核筛选。

建议将绿色“对齐通过”改为中性的“自动对齐完成”，绿色留给明确的人工确认。内容参考检查采用“参考一致”，校准采用“已校准，待复核”；不让最后运行的步骤覆盖其他维度的状态。语气词属于内容类型，按是否保留决定处理，不宜默认与严重错误同色。

不要显示“正确率 98%”这类未经标注集校准的数字。当前识别置信度、参考相似度和对齐可靠程度来源不同，详情里分别命名，不能互相替代或跨模型直接比较。

报告示例：`处理 232 条 · 自动完成 X · 沿用原时间 Y · 定位失败 Z · 待试听 N`，并列出拆条前后总数，说明类别是否重叠。提供“查看待复核”，跳到具体条目；保留任务报告入口，不让关键信息只在短暂提示里出现。

## 5. 保存、导出与查看路径

目前 Ctrl+S 保存内部工程 JSON，不等于写出 SRT；工程保存在 `data/projects`，项目列表的“打开”却打开素材/SRT 所在文件夹，导出成功仅短暂显示路径。这些行为需要明确区分。

- 保存按钮叫“保存工程”，显示“已保存 / 未保存 / 保存失败”；增加“工程另存为/备份”以便长期维护和迁移，SRT 导出继续是单独操作。
- 路径操作明确命名：“定位素材”“打开工程文件夹”“定位导出文件”“复制路径”，不再复用含义不清的“打开”。导出成功后保留结果卡片和最近导出记录。
- 导出前显示格式、文件名、实际目录、导出条数和待复核条数；默认记住最近目录，可选素材同目录，重名继续自动另存。普通质量警告不自动排除条目；无效时间等无法生成有效文件的问题仍需修复。
- 素材移走后允许打开工程、查看和导出已有字幕，并提供“重新关联素材”；不能让项目入口整项禁用。
- 自动保存继续保留 revision 冲突保护；增加本地恢复草稿和定期备份，不能依赖关闭页面时的大请求保存。
- 长期安装版建议将程序与数据位置解耦：工程默认放用户可选择的文档目录；模型、引擎、缓存和日志分别配置，提供位置与占用查看。内部应用数据位置必须可在设置中直接打开，文件树不隐藏。迁移旧数据时先列明位置、备份、校验，再切换；本轮不迁移。
- 当前按用户安装到可写目录可用，但依赖仍在安装目录创建。应检查“旧安装位置继承”、升级正在运行的服务、覆盖本机 `config/ui.json`、Python 升级后旧 venv/引擎的重建策略，避免安装成功而下次启动失败。发布默认设置应由模板生成，不直接带开发机最后一次界面参数。

依据：[paths.py](../backend/core/paths.py)、[app.py](../backend/app.py)、[安装器](../installer/SubtitleStudio.iss)。数据路径重构是后续方案，不改变已经确认的“EXE 安装、启动下载依赖、界面下载模型”发布方式。

## 6. 性能与维护顺序

1. **先消除编辑卡顿**：字幕表目前整表生成 `innerHTML`，`updateButtons` 还扫描所有行；单条编辑、勾选先局部更新，长列表再做虚拟滚动。历史 5000 条首渲染约 665 ms，非本轮复测；虚拟化必须保留编辑焦点、选择、定位和撤销。
2. **复用声学证据**：同一音轨的重叠区间会反复跑 VAD；先合并窗口并缓存帧级概率，键包括音频指纹、采样率和参数。继续复用已有 PCM 缓存，不重复建设。记录 VAD 退化到 RMS 的原因，避免悄悄退化后仍呈现相同质量结论。
3. **按测量选批量推理**：Whisper 已有模型缓存，外部引擎每次任务新进程加载模型。先分开记录解码、模型加载、推理和后处理用时，再评估同引擎任务复用进程；保留空闲释放、取消和显存上限。批量推理从小批次评估，并记录峰值显存及结果差异。[faster-whisper 官方批量接口](https://github.com/SYSTRAN/faster-whisper#batched-transcription)
4. **播放定位**：当前每次查找线性扫描字幕；确有瓶颈时为排序后的时间建立索引，处理乱序和重叠，不直接换成假定不重叠的二分搜索。
5. **可靠性优先**：参考结果绑定剧本指纹、模型下载加跨进程锁、导出路径竞争处理、缓存清理先预览并保护工程/模型。这些比更换匹配算法更紧迫。
6. **逐步拆模块**：`app.js` 同时处理状态、保存、任务、时间轴和渲染，后续按职责抽模块，并统一状态与质量检查数据；保留现有原生前端，不为整理目录引入构建框架。

## 7. 验收与实施批次

先建立一组经人工核对的 20–30 段素材：安静对白、配乐、突发音效、轻声、拖音、多人重叠、长静音、中英数字与连续短句。优先加入 #213、#225、#195 所在区间，保留相邻台词和原音频，固定标注版本。

每次只比较一个主要变量，分别统计：中文 CER/漏字/多字、起止偏差的中位数及 P95、异常尾部持续时间、裁掉发声的次数、异常长条数量、需要人工处理的条数、实时率与峰值内存/显存。边界合格容差先由实际素材与人工需求确定，不凭自动化测试数量宣布准确。

| 批次 | 范围 | 完成依据 |
|---|---|---|
| 第一批 P0 | 复现长条与词时间异常；内容确认不遮时间问题；统计统一；预览与导出时间明确一致 | 当前异常逐条能定位、解释或进入复核；导出时间与界面承诺一致；原字幕可恢复 |
| 第二批 P1 | 异常片段重试、边界与分块改进；复核导航；参考差异；保存/路径体验 | 对照标注集减少长尾与人工处理，且不增加漏字、切字；移动素材仍可恢复工程 |
| 第三批 P2 | 表格局部更新/虚拟化、VAD 缓存、推理批量与进程复用 | 同机同素材测量交互延迟、总耗时和资源，确认收益后启用 |

原工程作为检查基线保留，不自动重写；未删除文件、隐藏目录或用时长上限强裁字幕。异常片段重试、真实模型评测、完整的内容/时间人工确认流程和性能改造仍需后续实施。
